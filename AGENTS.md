# AI Agent Guidelines for Duely Codebase

Welcome! This document provides essential knowledge for AI agents working on the Duely project. By following these conventions, you ensure your implementations match the existing architecture and align with the project's unique practices.

## 🏗️ System Architecture & Big Picture
- **Stack**: React 19 (TypeScript, Vite 7, Tailwind CSS 4) + Spring Boot 4.1 (Java 21, Jackson 3, Hibernate 7). Postgres 15 and Valkey 8.
- **Core Entity Flow**: `Bracket` has many `Item`s and `Result`s. Entities are persistence only: controllers return view classes (`BracketDto`, `ItemDto`, `ResultDto`, each with a static `from(entity)`) or aggregation DTOs (`ItemRankingDto`, `CommentDto`), and the Valkey cache holds those same views. A new entity field is therefore private until a view names it; the owner (`createdBy`), `Result.userId`, the ticket nonce and `counted` are in no view, so ownership checks read the repository (`service/BracketAccess` does). Cached views are plain non-final classes with getters and setters, not records: the cache serialiser only writes type information for non-final classes. Request bodies are records with Bean Validation (no MapStruct). A report's `reporter_uid` never leaves `ReportRepository`.
- **Network Proxying (CRITICAL PITFALL)**:
  - In Docker, `nginx` serves on port 3000 and maps `/api/*` to `http://backend:8080/*` (stripping the `/api` prefix). Actuator (health checks, `/actuator/prometheus`) is on the management port 8081, which nginx never proxies and Compose never publishes; tests share the application's port (`application-test.properties`).
  - The backend controllers (like `BracketController`) have **no prefix** mapped (`@GetMapping("/brackets")`, NOT `/api/brackets`).
  - Locally, the Vite dev server mirrors this: `/api/*` is proxied to `http://localhost:8080` with the prefix stripped, and `VITE_API_URL` defaults to `/api`.
  - nginx forwards the browser's scheme and port (`X-Forwarded-Proto/Port`, https/443 behind the Cloudflare tunnel) so Spring treats tunnel requests as same-origin. Only `TRUSTED_PROXIES` may set the client address (`X-Forwarded-For`, or `REAL_IP_HEADER`): the tunnel container's fixed 172.29.53.250 in development and in `docker-compose.tunnel.yml`, or a provider's load balancer. `frontend/runtime-config.sh` writes it, `$public_origin` and the optional Firebase sign-in proxy (`FIREBASE_AUTH_PROXY`: `/__/auth/` on this site, named in `<meta name="auth-domain">`) into nginx's config at container start, so the images stay deployment-neutral.
- **Deployment**: `docker-compose.yml` builds from source for development; `docker-compose.prod.yml` runs the GHCR images at `DUELY_TAG` with the backup service (`deploy/backup.sh`), and `docker-compose.tunnel.yml` adds the named tunnel. `PUBLIC_BASE_URL` (`app.public-base-url`) is the only source of the site's origin: `PageHeads` (canonicals, JSON-LD, `<meta name="public-origin">`), the sitemap and `/robots.txt` (both `SitemapController`) and the SPA's `publicOrigin()` in `PageMeta.tsx` all use it, never the Host header (the SPA falls back to its own origin only when the tag is empty or names a loopback host). Production sets `app.require-public-origin`, so a localhost origin stops the backend. Shell scripts are LF (`.gitattributes`); everything else is CRLF in the working tree.
- **Runs and rankings**: the server is authoritative. `POST /brackets/{id}/runs` picks the entrants and returns a signed ticket (`service/RunTickets`, stateless HMAC; its nonce is the idempotency token); `POST /brackets/{id}/results` takes `{ticket, matches}` and `scoring/RunScoring` derives the ranking from the matches. Entries knocked out in the same round tie and share the tier score `(n-1 - (a+b)/2)/(n-1)`. Every valid run is saved; only **counted** runs (`results.counted`, hidden from JSON) touch `item_stats` and the run count: not faster than 0.4 s per match, within the per-bracket daily quotas (via `RateLimiter.tryConsume`): `counted-user` when signed in, then `counted-ip` for every run, signed in or not, so signing in or out never adds to an address's allowance (a run the user quota refuses doesn't charge the address). A guest's uncounted run (`counted = false AND user_id IS NULL`) is deleted by `RunPruner` (hourly, `app.runs.prune-cron`) once its ticket can no longer be replayed (`RunTickets.MAX_AGE` plus an hour); signed-in players' runs stay as their history. The leaderboard is `item_stats`, updated by `ItemStatsRepository.applyRun` in the same transaction as the result under a shared per-bracket advisory lock; `StatsService.rebuild` recomputes it under the exclusive lock, and bumping `StatsService.STATS_VERSION` rebuilds every bracket on the next startup, so a scoring change reaches history. Sort order is `scoring/Leaderboard` (mean shrunk towards 0.5 by 5 runs, exposed as `score`; the raw mean is `averageScore`). `frontend/src/utils/rankings.ts` and `tournament.ts` mirror the scoring, order and bracket sizes; both suites check `shared/*.json`, so change a rule there first.
- **Moderation and visibility**: a bracket with `hidden_at` set exists only for its owner and admins. Every per-bracket endpoint (reads, runs, results, reports) goes through `BracketAccess.requireVisible`; pages call `findVisible(id, null)`, so they are a 404 for everyone. List queries filter `hidden_at IS NULL`. Owner-or-admin changes use `requireOwnerOrAdmin` (403, or 404 for a hidden bracket). Deletes cascade in the database (`items`, `results`, `item_stats` foreign keys); removing a run goes through `StatsService.rebuild(bracketId, change)` so the leaderboard is rebuilt in the same transaction. Acting on a target (`ModerationService`) resolves the open reports about it. A report points at a bracket or a comment (a result id, which is `CommentDto.id`); reasons are `model/ReportReasons`, mirrored by `frontend/src/utils/reports.ts` and checked against `shared/report-reasons.json`.
- **Lists and counters**: no endpoint returns an unbounded list. `GET /brackets` and `/me/brackets` take `BracketListQuery` (`sort=newest|oldest|popular|name`, `type`, `category`, `q`, `page`, `size` ≤ 50) and return `BracketPageDto`; `/home` is one cached `HomeDto`; `/me/results` needs a `bracketId` and returns the latest 100. The SQL lives in `repository/BracketListRepository`, whose `LISTED` predicate (`hidden_at IS NULL AND item_count >= 2`, "playable") must stay literal SQL so the partial indexes match. `brackets.item_count`, `run_count` and `last_run_at` are counters: set at creation, changed only by SQL in the transaction that changes what they count (`BracketRepository.addCountedRun` with a counted run, `setRunCounters` in `StatsService.rebuild`), never by saving the entity (`updatable = false`). A bracket inserted by hand needs its `item_count`, or it stays off the lists.
- **Caching (`Valkey`)**: Spring `@Cacheable`/`@CacheEvict` backed by Valkey with absolute TTLs (`CacheConfig.CACHES`). Every write must evict exactly the keys it changes; where the keys are only known at run time (moderation, account deletion, rebuilds), use `config/CacheEvictor` after the transaction commits (a run evicts in `RunService.evictAfterRun`, according to whether it counted and carries a comment). The one deliberate exception is `bracketPages` (unfiltered first pages) and `home`: cleared when a bracket appears or goes (`CacheEvictor.clearLists`), but not per run, so their two-minute TTL bounds how stale run counts get. Cache writes are immediate (`immediateWrites()` in `CacheConfig`): Lettuce's default is fire-and-forget, which lets a read's put land after a later eviction. Unknown cache names fail fast. If the cached JSON shape changes, bump `KEY_PREFIX` in `CacheConfig`. Browsers never cache API responses (Spring Security's default `no-store`).
- **Rate limiting**: `ratelimit/RateLimiter` keeps fixed-window counters in Valkey (`app.rate-limit.buckets.*`) through `RateLimitStore`: its own connection (`app.rate-limit.valkey.*`, `LIMITS_VALKEY_*`), which Compose points at `valkey-limits`, a second Valkey that never evicts, so filling the cache's (LRU) instance cannot reset a quota. Unset, it uses the cache's connection details. Never expose its connection factory as a bean: Boot's own `RedisConnectionFactory` backs off when one exists. Call `rateLimiter.tryAcquire(bucket, subject)` in controllers; GETs are limited by `ReadRateLimitInterceptor`. A guest's subject is always `ClientSubject.of(request)` (IPv4 as is, IPv6 per /64, IPv4-mapped unwrapped), never `getRemoteAddr()` itself. When the limits Valkey is unreachable or full only `read` fails open; every other bucket keeps counting in a bounded in-process map on each instance.

## 🧑‍💻 Developer Workflows
- **Backend Testing**: `mvn verify` inside `/backend` (no Maven wrapper; Docker must be running). Unit tests are `*Test` (surefire), integration tests are `*IT` (failsafe) and extend `support/IntegrationTest`, which starts Postgres and Valkey in Testcontainers (`@ServiceConnection`), mocks Firebase with `@MockitoBean FirebaseAuth` (fake tokens `USER_A`, `USER_B`, `USER_C`, `ADMIN`) and keeps tests off the network with `FakeDnsConfig`: fake DNS, and `FakeUpstreamHttp` (the `upstream` field) for the scraped YouTube and Spotify pages, reset before each test together with `UpstreamGuard`'s breakers. Any other Spring context test must mock `FirebaseAuth` too, since `FirebaseConfig` refuses to start without credentials.
- **Frontend Testing**: Vitest with `@testing-library/react`: `npm run typecheck && npm run lint && npm test` inside `/frontend`. ESLint (`eslint.config.js`: type-aware typescript-eslint, `react-hooks`, `jsx-a11y`) allows no warnings in CI; disable a rule on a line only with a comment saying why. Keep the latest value of a prop or state for callbacks with `useLatest`, never by writing a ref during render. Pure logic (tournament, rankings, media URLs) lives in `src/utils` with unit tests next to it.
- **Shared test vectors**: where the frontend mirrors a backend rule, the cases live once in `shared/*.json` and both suites read them (`support/SharedFixtures` in JUnit, `utils/sharedFixtures.ts` in Vitest). Add a case there, not to one side.
- **Database Migrations**: Changes to schema **MUST** be implemented using Liquibase XML changelogs in `backend/src/main/resources/db/changelog/`. Do not rely on `hibernate.ddl-auto=update`.
- **Dependencies**: Dependabot (`.github/dependabot.yml`) proposes weekly updates for Maven, npm, both Dockerfiles, the Compose images and actions; base images are exact versions. `frontend/package.json` overrides `@grpc/grpc-js` because Firebase still pins a vulnerable version (Firestore isn't used), and typescript-eslint's `minimatch` (dev only). Keep `npm audit --omit=dev` clean; CI runs it.
- **Metrics**: counters go through Micrometer's `MeterRegistry`, named `duely.<area>.<what>` with low-cardinality tags (a bucket, a reason, an upstream; never a user, address or bracket id). They show up at `/actuator/prometheus` as `duely_<area>_<what>_total`.

## 📦 Project-Specific Conventions & Patterns
- **Security & Firebase**:
  - Token-based auth via `FirebaseAuthenticationFilter` (built in `SecurityConfig`, not a `@Component`). Get the caller with `CurrentUser.uidOrNull(authentication)`: the Firebase uid, or null for guests. No `Authorization` header means a guest. A bearer token that fails verification is a `401` (`WWW-Authenticate: Bearer error="invalid_token"`) on writes, so a signed-in player's run is never saved as a guest's; on `GET`/`HEAD`/`OPTIONS` it degrades to anonymous. `api.ts` refreshes the token and retries a 401 once.
  - There is no CSRF layer, deliberately: the bearer token travels in the `Authorization` header, which browsers never attach cross-site. Don't add cookie-based auth without revisiting this.
  - Errors go through `GlobalExceptionHandler`: throw `ResponseStatusException` (404/403/409), `InvalidRequestException` (400 with a field `errors` map) or `RateLimitExceededException` (429 with `Retry-After`). `IllegalArgumentException` is not a client error: it falls through to the logged 500.
- **Input Sanitization**:
  - All user text (names, descriptions, titles, comments) goes through `Sanitizer.stripToPlain`, which only normalises plain text (NFC, newlines, control characters, trimming, length). It does **not** strip markup or decode entities: `x<y`, `<b>` and `&amp;` are stored exactly as typed.
  - Rendering as text is therefore the only defence, by design. **Never use `dangerouslySetInnerHTML` (or any HTML sink) for user content**; on the server it goes through jsoup's text/attribute setters or `JsonLd`, never as HTML.
  - Bracket categories are a fixed list (`model/Categories`, mirrored by `frontend/src/utils/categories.ts`, both checked against `shared/categories.json`). Anything else is a 400 on `category`.
- **Media URLs**: `media/MediaUrlValidator` checks every stored URL: https only, public hosts (resolved once per host per request; at most `MAX_HOSTS` (20) hosts per request, all lookups within `DNS_BUDGET`), and per type: `video` must be a YouTube link with an extractable id, `song` is Spotify (no `spotify.link`) or an audio URL, `image` any public https URL. The DNS check is hygiene at creation, not a security boundary. `frontend/src/utils/mediaUtils.ts` mirrors these rules (the host cap via `shared/media-hosts.json`). User-supplied images load with `referrerPolicy="no-referrer"`; YouTube plays from `youtube-nocookie.com` (`YOUTUBE_EMBED_ORIGIN`).
- **Scraping**: `MediaMetadataService` scrapes YouTube search and Spotify embeds through `UpstreamHttp`, inside `UpstreamGuard.call` (four at once per instance, a breaker per upstream). Throw `UpstreamGuard.Failure` for an unusable answer (markup changed, error status) so it counts against the breaker; a business answer such as a missing playlist is not a failure. "No match" is cached (`youtubeNoMatch`, 1 h); failures never are. Requests run on virtual threads (`spring.threads.virtual.enabled`), so bound slow work explicitly rather than relying on a thread pool.
- **Frontend State**:
  - `apiCache.ts` is a small TTL cache. Per-user keys include the uid. List pages are keyed by their query string and dropped together with `invalidatePrefix`. To wipe it on sign-in changes, use `resetApiAuthState()` in `api.ts` (AuthContext already does).
  - Use `useAuth().currentUser` for the signed-in user. `currentUser.isAdmin` (from the token's claims) only decides whether admin controls show; the server checks every admin call. Guests' own runs live in `SessionBattleContext` (sessionStorage).
  - Show distinct loading, error (with retry) and empty states; never render "not found" or "no brackets" for a failed request. Use `errorMessage()` from `api.ts` for the server's message. Requests time out after 15 s (30 s for the endpoints that wait on YouTube, Spotify or DNS); `apiCache.getOrLoad` shares a load already in flight. An `ErrorBoundary` around the routes catches render errors and reloads once when a lazy chunk vanished after a deploy.
  - Use `randomId()` (not `crypto.randomUUID`, which needs a secure context) for client ids. Runs need no client token: the server's run ticket is the idempotency key.
  - A run in progress is saved per bracket in sessionStorage (`utils/runProgress`: ticket, entrants, picks) and rebuilt by replaying the picks; clear it once the run is saved or abandoned. The create form keeps its draft in localStorage (`utils/createDraft`) until the bracket exists. Both go through `utils/storage`, which never throws.
  - Sign-in: `signInWithGoogle` uses the popup, and the redirect where popups don't work (`auth/popup-blocked`, or `isInAppBrowser()`); anything a redirect would lose must already be in storage.
  - `/privacy` says what is stored and who sees what. Change it when a change stores something new, keeps it longer, or loads a new third party.

Follow these patterns strictly to remain productive and maintain project coherence!
